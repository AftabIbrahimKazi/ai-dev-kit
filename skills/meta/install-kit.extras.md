# Install kit extras

Read only when migrating renamed skills, adding a signature or company standards, archiving, uninstalling or updating an install.

## Step 3b — Migrate renamed skills (every re-install; mechanical with an approval gate)
The library keeps a rename ledger at `migrations/RENAMES.md` (repo root). On every `update` run, the script compares the target's `.ai-dev-kit.json` manifest against the ledger's **Old name** column itself and reports any match as a *pending* migration — it never renames anything without approval:
```
node <library>/skills/meta/install-kit.cli.js update --library <library> --root <target>
```
If the output lists a pending migration, show the old → new name to the user and ask. On approval, re-run with `--apply-migrations old-name1,old-name2` (or `--apply-migrations all` once the user has approved everything shown). That one flag copies the new-name skill in with its companions, carries `learnings.md` forward from the old folder (the one exception to "never copy learnings" — it's a move within the same project), and deletes the old folder only after the new one lands. Still grep the routed session-protocol file (and any multi-tool pointer file), plus the other skills' text, for the old name and update references by hand — the script only touches skill folders. Report each migration in the Step 4 summary (`old-name → new-name, learnings carried, N references updated`).
When maintaining the library itself: any skill rename/merge MUST add a ledger row in the same change — a rename without a ledger row strands every existing install.

## Step 3b2 — Project signature (optional watermark; the user decides)

Ask once after the standards question, via `AskUserQuestion` (single-select, header "Signature"): **No signature** (default), **Use a short alias** (the built-in "Other" box takes 2 to 6 letters). Say in one sentence what it does: it watermarks the code written to the standards with that alias, `abc-` classes and ids, `data-abc-` data attributes, `Abc` components, for the project's own code only, never packages or libraries. Never suggest or choose an alias yourself. Pass the answer as `--signature <alias>` or `--signature none`. It fills the project table's "Selector signature" row; `signature set|remove|show --root <target>` changes it later. `code-audit` rule `css-11` checks it against custom code only.

## Step 3c — Company standards (opt-in; mechanical)

Ask once, after the standards question, via `AskUserQuestion` (yes/no, header "Company standards"): "Does this project follow your own company's standards (a design system, style guide, standards docs)?" On no, skip this step. On yes, the kit keeps them in a separate `coding-standards/company/` folder and never edits the files in it.

1. Ask where the docs are (free text via "Other"; blank means the user will drop files in later).
2. Ask what happens to the kit's default standards (`AskUserQuestion`, single-select, header "Defaults"): **Install the default standards too** (`keep`, the safe default: company rules win on conflict), **Don't install the default standards** (`drop`: company only, so skip the Step 3 questions and do not pass `--standards`), **Auto-detect** (`auto`). Before showing auto-detect, say in one sentence that it guesses from file names, titles and headings, never removes the accessibility, QA, git or versioning defaults, and is reversible.
3. Run: `node <library>/skills/meta/install-kit.cli.js company sync --library <library> --root <target> --company-from <folder> --company-defaults keep|drop|auto` (or add the same three flags to `install`). With auto, show the user the returned `findings` table and the `disclaimer`, and offer `--company-defaults keep` if they disagree.
4. It writes `coding-standards/company/INDEX.md` (routing table; imports the company's own "build X, read Y" table when it has one), a `company-standards` skill, a marked block in the session-protocol file, and a manifest record. Report `files`, `routes`, `dropped`.

Later: `company sync` after the folder changes, `company status`, `company remove` (restores removed defaults, keeps the user's docs; `--purge` deletes them). The `standards-chain` mod requires `INDEX.md` to be read before code or UI edits, and does not demand a default file the company replaced.

## Step 5 — Archive / unarchive (mount / unmount) a skill
Archiving is automatic: the `skill-scope` session-start hook archives the per-session-archivable set, the prompt hook restores a skill when the message names its trigger, and `/next <task>` does both on demand (all through `skill-scope/auto.js`, which calls the commands below). Never hand-move those folders. To move one named skill yourself, run:
```
node <library>/skills/meta/install-kit.cli.js archive   --root <target> --skills name1,name2   # or --all
node <library>/skills/meta/install-kit.cli.js unarchive --root <target> --skills name1,name2   # or --all
```
`archive` moves exactly the named skills (only ones the manifest tracks as currently installed — same protection as `uninstall`) from `<skill-root>/<name>/` to `<tool-dir>/skills-archive/<name>/` (`.claude/skills-archive/` or `.opencode/skills-archive/`, sibling of the skill root, matching `skill-scope`'s existing convention), drops the CommonJS shield once nothing archived still needs it, and records the move in the manifest. `unarchive` reverses it by name (or `--all` to restore everything currently archived), re-adding the shield if a restored skill needs it. A skill the manifest doesn't recognize as installed, or doesn't recognize as archived, is reported back and left untouched rather than guessed at. `handover` records the archived list + paths in `handover.md` as it always did; the script just makes the move itself atomic and reversible instead of a narrated multi-file move.

## Step 6 — Uninstall
```
node <library>/skills/meta/install-kit.cli.js uninstall --root <target> --skills name1,name2   # or --all   [--remove-hooks] [--remove-standards]
```
Kit hooks in `.claude/settings.json` stay unless `--remove-hooks` is passed, which removes only entries identical to the kit's own and keeps every other hook and setting. Removes exactly the skill folders the manifest (`.ai-dev-kit.json`) recorded this kit as having installed, active or archived (an archived skill is removed from `skills-archive/`, and an empty `skills-archive/` goes with it) — never a folder the manifest doesn't know about, even if `--all` is passed, so a hand-authored or third-party skill living in the same skill root is always left alone. Drops the `package.json` CommonJS shield once no remaining companion needs it. **Never removes `coding-standards/` or the session-protocol file by default** — pass `--remove-standards` to also remove `coding-standards/`; the session-protocol file is never deleted by the script under any flag, since it may carry project-specific edits beyond what the kit wrote. If the user wants it gone too, remove it yourself after confirming with them, not automatically. Report what was removed and what was deliberately left, straight from the script's `removed`/`kept` output.

## Keeping installs current
This copies a snapshot, tracked by the manifest. `update --all` also refreshes archived skills in place and leaves them archived, and adds any hook block a newer kit ships to `.claude/settings.json` when the project already holds a kit hook (a project that never opted in is left alone); `install` of an archived skill makes it active again. When the library improves, or the user wants more skills, commands, addons or mods later, run `update` (add `--skills` for specific ones, or `--all` to resync everything the manifest already tracks) — the manifest ensures only kit-managed files move. Never edit an installed copy directly for library-wide improvements; edit the library and re-install/update.

**What's new.** `update` returns a `whatsNew` block: the `CHANGELOG.md` entries newer than the date this project last saw (`lastSeen` in the manifest, set by `install` and advanced by every `update`). Show it as a footnote after the update summary: one line per entry (`entries`, each `date kind: headline`), then "and N more" from `more`. It is information only: ask nothing and install nothing because of it. When `baseline` is true the project had no recorded date, so the entries are just the two newest sections; say tracking starts now. If `whatsNew` is absent or `entries` is empty, print nothing.


**Running `install-kit.cli.js` yourself, in plain words.** Open a terminal in your project folder and type `node path/to/ai-dev-kit/skills/meta/install-kit.cli.js install`, then press Enter. Each question is a menu: press Up and Down to move, Space to tick a box, Enter to confirm. Left arrow (or Backspace) undoes the last answer and shows it again so you can change it; Right arrow replays an answer you just went back over; `q` quits. Each screen says "Step 3 of 9" and lists the keys that work there. Before anything is written you see all your answers, then pick Install, Change an answer or Cancel; Cancel writes nothing. Add `--yes` to accept every recommended answer without a menu (for scripts), and `AI_DEV_KIT_NO_MENUS=1` to get plain numbered questions instead of arrow-key menus. If you pick company standards or the default standards, the installer also asks for a Context code and writes the `[CX]` rule into your CLAUDE.md, whichever standards path you choose; `install-kit.verify` checks it.

**Hidden-state reviewer.** If `implicit-state-audit` is installed, the installer asks who may read a file the free scan flagged: Auto (Gemini first, then a local Ollama model; free-tier Gemini may keep what it is sent), Ollama only (nothing leaves your machine), or Static scan only (no AI). Auto is pre-selected, but `--yes` always picks Static. `--reviewer auto|ollama|static` sets it without a question. The choice is one small file, `.claude/state-audit.json`; delete it to go back to Static. `"commitGate": "warn"` or `"off"` in the same file softens the commit check, which otherwise blocks a commit that adds a loading + error + success flag trio.

**`--yes` and the standards system.** `--yes` takes every default, and the default for "Install the coding-standards system?" is No, so `install --yes` alone installs skills and commands but no `CLAUDE.md`, and the verify step reports that no session contract exists. For a fully verified unattended install add `--standards --context-code <2-4 chars>`.

## Opt-in categories

**Feature-usage tracking** is a choice the CLI asks at the end of an interactive install ("Keep track of which kit features get used?", then whether to show a one-line notice on first use) and takes as flags: `install-kit.cli.js install ... --usage on|off --usage-notify on|off`. It writes one small config file in the home folder (`~/.ai-dev-kit/usage/config.json`), never into the project, and only the optional `feature-usage` mod (Claude Code, via `mod-setup`) reads it. A script, not the model, records and reports it, so it costs no tokens. Pass the flags when you run the CLI yourself, as the prompts only appear on a real terminal. Later switches: `/kit-usage on|off|notify on|off|status|report`, or `session-budget/usage.js`.

**The `batch` mod** (one read-only tool, `mcp__batch__run`; see `mod-setup`) is reported on every install that includes `session-budget`, whose "Reading discipline" lines tell the model when to use it: the JSON result carries a `batch` block (`enabled`, `scope`, an install `hint`, and a `warning` when the mod is enabled without `session-budget`). `install-kit.cli.js install ... --batch on|off`, or `install-kit.cli.js mods --root <project> [--batch on|off]` on its own, runs `claude plugin install|uninstall batch@ai-dev-kit-mods --scope project` in the project; if that fails (for example the kit's marketplace is not added yet) the install still succeeds and the result carries the error and the two commands to run by hand. The CLI reads `enabledPlugins` in the user and project settings to tell whether it is enabled and never edits those files itself.

**Opt-in Claude Code mods** (`mods/` + `mod-setup`) are a sixth category: Claude Code targets only, never part of Everything/Pick/Auto-detect, never stack-scanned. Offer them only when the user asks (for example "set up mods", "track my token use"). Then install `mod-setup` and follow it in full; it owns the version check, the review of what each mod touches, and the install. A mod needs its engine script, which ships with a skill (`pre-commit`, `pre-merge-gate`, `session-budget`); Step 2 already installs those `.js` companions.

**`misfire-log`** (`meta/misfire-log.md` + its two scripts) is a seventh category: never part of Everything/Pick/Auto-detect, never stack-scanned. Offer it only when the user asks (for example "track when the kit doesn't work", "log misfires"). Install the skill file and both scripts, then follow its own Setup — create `.claude/misfires.jsonl` lazily and add it to `.gitignore`. No key, no service, no other skill depends on it.

**Opt-in slash commands and git hooks** are an eighth category: never part of Everything/Pick/Auto-detect. Offer only when asked ("add slash commands", "git hook", "enforce this for human commits"). Both run the kit's own scripts and need that script's skill installed first.
- **Commands** (`commands/*.md` templates): `install` copies them itself, so do not copy by hand. Claude Code → `<target>/.claude/commands/`, OpenCode → `<target>/.opencode/commands/`; Codex has no command folder, so it gets none. A command is copied when the skill its script runs is installed or archived (read from the template: `skill-scope/auto.js run <skill>` or `{{skill-root}}/<skill>/`; `kit` and `format` need nothing; `eta` and `dupe` need `plan-first`; `pickup` needs `handover`). Commands for an opt-in addon (`narration` for `narrate`, `persona` for `personality`, `ctx` and `figma` for `project-context`, `diagram` for `diagram`, `invariants` for `invariants`, `teardown` for `teardown`, `teardown-film` for `teardown-film`, `teardown-sound` for `teardown-sound`, `figma-code` for `figma-code`, `modern-web` for `modern-web`) are left to that addon's own setup. `{{skill-root}}` is replaced with the skill root as a relative path with forward slashes. The manifest records each copied file with a hash: `update` refreshes an unedited command and adds a newly eligible one, a command you edited is left alone (`--force` overwrites), a file the kit did not write is never overwritten, and `uninstall` removes unedited tracked commands (and a command whose skill was uninstalled). Pass `--no-commands` to skip all of this. The user then types `/audit`, `/commit-check`, `/quiet`, `/stale`, `/githooks`, `/pickup`, `/wrap-up`, `/next`, `/resolve-conflicts`, `/responsive-check`, `/optimize-assets`, `/version-bump`, `/perf`, `/e2e`, `/recon`, `/ctx`, `/figma`, `/diagram`, `/invariants`, `/teardown`, `/teardown-film`, `/teardown-sound`, `/figma-code`, `/eta`, `/format` or `/kit`; the script output is injected into the prompt, so no skill has to be matched first.
- **Git hooks** (works in every tool, and for human commits): after `pre-commit` is installed, ask via `AskUserQuestion` (yes/no, header "Git hook"), then on yes run `node <skill-root>/pre-commit/install-hook.js`. It refuses to overwrite a hook it did not write; `uninstall` removes only its own. Tell the user `--no-verify` skips hooks.

## Terminal fallback internals

**The CLI fallback's own skills question mirrors Step 1's modes, not a flat catalog dump.** It scans `--root` for `skill-scope`'s conditional-pinned signals (a `three`/`astro` package.json dependency, an `astro.config.*` file, a Shopify theme structure, an existing `memory-bank/` folder, `hooks-enforcement`'s settings already present) via `detectStackSignals()`, then offers three choices: **Auto-detect** (default — the universal + per-session-archivable group plus whatever matched, named with its evidence; if nothing matched, falls through to a `STACK_PRESETS` pick for Astro/Next.js/Laravel/none, same gaps as the table below, for a brand-new project with nothing yet to scan), **Everything** (`eligibleCatalogNames()` — every catalog skill outside the opt-in categories, no typing), or **Pick individually** (`pickSkillsByCategory()`). Pick individually loops rather than asking once: pick one of the nine `CATEGORY_ORDER` categories (`models/claude` and `models/opencode` both collapse to `models`), multiselect skills from it, see a running "Selected so far" tally printed in its own color (`cyan()`) so it reads as distinct from a plain skill name or a dimmed purpose, then either pick another category or finish; finishing early states plainly which categories were never reviewed (`yellow()` — "not reviewed, so not installed") instead of leaving it ambiguous whether they were skipped or swept in. Auto-detect and the preset path both ask one yes/no afterward ("Add any other skills on top of this set?") before falling back to that same looping picker, scoped to what wasn't already chosen. Model-lineup signals are deliberately not scanned (a judgment call, not a file check) — reachable only through Pick individually. Keep `UNIVERSAL_SKILLS`/`ARCHIVABLE_SKILLS`/`STACK_PRESETS`/`CATEGORY_ORDER`/`STANDARD_ROW_LABELS` in `install-kit.cli.ts` in sync with `skill-scope.md`, the Stack table below, and `coding-standards/CLAUDE.example.md`'s Active Standards table by hand; nothing here is derived automatically.

The terminal fallback's full color palette (all six helpers near the top of `install-kit.cli.ts`, each gated on `isInteractive()` and the `NO_COLOR` convention — never applied to the final `--json` output): `bold()` for the question line on every `ask*` prompt (the one constant anchor before a list of choices), `dim()` for secondary/explanatory text (a skill's purpose, a category's skill count, the "type numbers separated by commas" instructions), `cyan()` for the category picker's running "Selected so far" tally, `green()` for anything the tool found or assumed on the project's behalf (a detected stack signal and its evidence, the auto-detected target tool, the auto-assumed `--root`), `yellow()` for a notice worth a second look without being an error (a stack preset's known coding-standards gap, categories left unreviewed), and `red()` for actual failures (`main()`'s caught-error and usage-error output). Six distinct roles, not one dim/plain split, so the eye can tell what kind of line it's reading without parsing every word.

The same terminal fallback also asks, right after the standards yes/no: **which script standard applies** (TypeScript only / JavaScript only / JS and TS together, pre-selected from a `tsconfig.json` or a `typescript` package.json dependency) and **which of the eleven project-wide standards apply** (CSS/HTML/Git/Versioning/SEO/Performance/Accessibility/QA/AI — `askMultiselect`'s new `defaultAll` mode, so pressing Enter keeps all nine instead of picking none; most projects keep every row, this question exists for the real exceptions). Both get written straight into the Active Standards table at protocol-file-creation time via `applyActiveStandards()` — see Step 3 below, which Claude Code chat asks the same two questions for, so neither path leaves the table's placeholders for later manual cleanup.

Every multiselect/detected line also carries a one-line purpose, via `loadSkillPurposes()` reading straight from `skills/README.md`'s own Skill/Purpose tables (truncated to 80 chars; nested markdown links in a cell flatten to their link text, since a relative `.md` path means nothing printed in a terminal), dimmed with an ANSI escape (`dim()`, respects `NO_COLOR`) so it reads as secondary to the skill name next to it rather than blending into one flat line — so a human picking skills in a bare terminal is never choosing bare names blind. Keeping `skills/README.md`'s tables current (the catalogs-to-update-together rule already applies) is what keeps these descriptions accurate; a skill with no matching row just shows its bare name.
