# Install Kit — Skills & Standards Into Any Project

Installs by copying markdown files only. Never installs packages, never runs build tooling, never touches project code.

**This skill runs from the library, not from inside the target.** Unlike other skills, `install-kit` is never copied into a project's skill root — there is no bootstrapping benefit to it (the mechanical work below runs as `node <library>/skills/meta/install-kit.cli.js ...` against `--root <target>` from wherever the library clone lives), and leaving it out of the target means there is nothing to self-remove and no `--finish` step. The decisions below (mode, which skills, stack confirmation, addon/MCP/mod opt-ins, the comment-style level, the context code) are still made in conversation; the script only executes the copying, merging, and verifying once those decisions are made.

## Self-improvement (do this first and last)
1. **At start:** read `install-kit.learnings.md` next to this file in the library (`skills/meta/`) if it exists. Apply relevant lessons.
2. **At end of every use:** append one dated bullet to that same file — source-location changes, a picking pattern the user prefers, a gap the script didn't cover. Merge instead of duplicating; delete disproven bullets. This is a library-wide file now (install-kit is never copied per-project), so a lesson learned on one project benefits every future install.

## Source locations (verify, don't assume)
- **Canonical home: the `ai-dev-kit` repo** — `My Projects/ai-dev-kit/` locally, `github.com/AftabIbrahimKazi/ai-dev-kit` remote (formerly `claude-dev-kit`; old URL redirects). It contains both `skills/` (category subfolders: `models/`, `workflow/`, `standards/`, `memory/`, `stack/`, `libraries/`, `meta/`, `addons/`, `mcp/`, with a README index) and `coding-standards/` (has `index.md` at its root).

Copies inside other projects are *installs*, not the source — improvements flow repo → projects, never the reverse. Pass this path as `--library` to every `install-kit.cli.js` call.

## Skill scope — read before Step 1

Every skill installed here falls into one of two mechanisms, defined canonically in the `skill-scope` skill — **read it now**, don't re-derive the classification. Summary:
- **Permanent-pinned** (universal, or conditional on this project's stack/tooling/model) — decided once, here, at install.
- **Per-session archivable** (task-instance-specific) — installed here too, but its per-session on/off toggle is `handover`'s job, not install-kit's. Install it now regardless; don't pre-filter it out at install time.

The user can override any pin decision, but only by stating it explicitly in this session — never infer an override from context or convenience.

**Opt-in addons** (`addons/` — currently `system1-prefilter`, `project-context`, `narrate`, `personality`) are a fourth category: never offered as part of Everything/Pick/Auto-detect by default, never stack-scanned. Offer them only when the user explicitly asks (at install or any later session) — then follow that addon's own Setup section for its install questions (e.g. `system1-prefilter` asks endpoint + API-key-variable questions itself; its local-Laya path has install-kit run the companion `laya-ctl.js` setup — only after the user approves the stated download size). Once installed, treat as permanent-pinned — it's the user's own durable choice, not re-derived per session.

**Opt-in MCP servers** (`mcp/` — `mcp-manager` + its `mcp-manager.<server>.md` companions) are a fifth category: never part of Everything/Pick/Auto-detect, never stack-scanned. At the end of Step 1, ask via `AskUserQuestion` (yes/no, header "MCP servers"): "Set up optional MCP servers (e.g. Stitch for UI prototyping)?" Yes → install `mcp-manager` and only the chosen server companions (Step 2 companion rule), then **run `mcp-manager`'s Setup interview in full** — it owns every question (servers, AI tools, scope, keys, routing, load mode) and the config writes; install-kit never asks them on its behalf. No → skip silently; the user can ask any later session. Once configured, treat as permanent-pinned.

**Opt-in Claude Code mods** (`mods/` + `mod-setup`) are a sixth category: Claude Code targets only, never part of Everything/Pick/Auto-detect, never stack-scanned. Offer them only when the user asks (for example "set up mods", "track my token use"). Then install `mod-setup` and follow it in full; it owns the version check, the review of what each mod touches, and the install. A mod needs its engine script, which ships with a skill (`pre-commit`, `pre-merge-gate`, `session-budget`); Step 2 already installs those `.js` companions.

**`misfire-log`** (`meta/misfire-log.md` + its two scripts) is a seventh category: never part of Everything/Pick/Auto-detect, never stack-scanned. Offer it only when the user asks (for example "track when the kit doesn't work", "log misfires"). Install the skill file and both scripts, then follow its own Setup — create `.claude/misfires.jsonl` lazily and add it to `.gitignore`. No key, no service, no other skill depends on it.

**Opt-in slash commands and git hooks** are an eighth category: never part of Everything/Pick/Auto-detect. Offer only when asked ("add slash commands", "git hook", "enforce this for human commits"). Both run the kit's own scripts and need that script's skill installed first.
- **Commands** (`commands/*.md` templates): Claude Code → `<target>/.claude/commands/`, OpenCode → `<target>/.opencode/commands/`; Codex/agents.md tools have no command folder, so skip. Copy a template only when its script's skill is installed (`audit` needs `code-audit`; `commit-check` and `hooks` need `pre-commit`; `token-report` and `quiet` need `session-budget`; `stale` needs `memory-gardener`; `resume` and `wrap-up` need `handover`; `eta` needs `plan-first`; `resolve-conflicts` needs `resolve-conflicts`; `responsive-check` needs `responsive-check`; `optimize-assets` needs `optimize-assets`; `version-bump` needs `version-bump`; `ctx` and `figma` need `project-context`; `narration` needs the `narrate` addon (its own setup asks commands, hotkeys or both, and installs the command itself); `persona` needs the `personality` addon; `kit` and `format` need nothing). Replace `{{skill-root}}` with the routed skill root as a relative path with forward slashes. Never overwrite an existing command file. The user then types `/audit`, `/commit-check`, `/token-report`, `/quiet`, `/stale`, `/githooks`, `/pickup`, `/wrap-up`, `/resolve-conflicts`, `/responsive-check`, `/optimize-assets`, `/version-bump`, `/ctx`, `/figma`, `/eta`, `/format` or `/kit`; the script output is injected into the prompt, so no skill has to be matched first.
- **Git hooks** (works in every tool, and for human commits): after `pre-commit` is installed, ask via `AskUserQuestion` (yes/no, header "Git hook"), then on yes run `node <skill-root>/pre-commit/install-hook.js`. It refuses to overwrite a hook it did not write; `uninstall` removes only its own. Tell the user `--no-verify` skips hooks.

## Click-first interaction
Every question in this skill defaults to the `AskUserQuestion` tool, not a typed prose question: ≤4 mutually exclusive options per question (its built-in "Other" choice is the typing fallback, never a separate open question), `multiSelect` where choices aren't exclusive, and a clearly-better option marked "(Recommended)" first when one genuinely is. The goal is an install the user can finish by clicking end to end. Typing stays unavoidable only for: override specifics once the user says "yes, override something" (Step 1), a hand-picked skill list when a Pick-mode category has too many skills for bundles to cover (Step 1), and a context code if the user rejects every generated suggestion (Step 3) — and even those go through "Other" rather than opening as a bare question.

`AskUserQuestion` only exists inside a Claude Code chat session. When this skill (or its mechanical half) is driven from a tool with no equivalent widget — OpenCode, Codex, or a human running `install-kit.cli.js` directly in a bare terminal — the CLI itself falls back to a plain numbered-menu prompt (built on Node's own `readline`, no package install required) for exactly the flags that were left out, the moment it detects a real TTY on both stdin and stdout. Nothing changes for Claude Code: it always passes every flag explicitly, so that fallback never triggers for it.

**The CLI fallback's own skills question mirrors Step 1's modes, not a flat catalog dump.** It scans `--root` for `skill-scope`'s conditional-pinned signals (a `three`/`astro` package.json dependency, an `astro.config.*` file, a Shopify theme structure, an existing `memory-bank/` folder, `hooks-enforcement`'s settings already present) via `detectStackSignals()`, then offers three choices: **Auto-detect** (default — the universal + per-session-archivable group plus whatever matched, named with its evidence; if nothing matched, falls through to a `STACK_PRESETS` pick for Astro/Next.js/Laravel/none, same gaps as the table below, for a brand-new project with nothing yet to scan), **Everything** (`eligibleCatalogNames()` — every catalog skill outside the opt-in categories, no typing), or **Pick individually** (`pickSkillsByCategory()`). Pick individually loops rather than asking once: pick one of the nine `CATEGORY_ORDER` categories (`models/claude` and `models/opencode` both collapse to `models`), multiselect skills from it, see a running "Selected so far" tally printed in its own color (`cyan()`) so it reads as distinct from a plain skill name or a dimmed purpose, then either pick another category or finish; finishing early states plainly which categories were never reviewed (`yellow()` — "not reviewed, so not installed") instead of leaving it ambiguous whether they were skipped or swept in. Auto-detect and the preset path both ask one yes/no afterward ("Add any other skills on top of this set?") before falling back to that same looping picker, scoped to what wasn't already chosen. Model-lineup signals are deliberately not scanned (a judgment call, not a file check) — reachable only through Pick individually. Keep `UNIVERSAL_SKILLS`/`ARCHIVABLE_SKILLS`/`STACK_PRESETS`/`CATEGORY_ORDER`/`STANDARD_ROW_LABELS` in `install-kit.cli.ts` in sync with `skill-scope.md`, the Stack table below, and `coding-standards/CLAUDE.example.md`'s Active Standards table by hand; nothing here is derived automatically.

The terminal fallback's full color palette (all six helpers near the top of `install-kit.cli.ts`, each gated on `isInteractive()` and the `NO_COLOR` convention — never applied to the final `--json` output): `bold()` for the question line on every `ask*` prompt (the one constant anchor before a list of choices), `dim()` for secondary/explanatory text (a skill's purpose, a category's skill count, the "type numbers separated by commas" instructions), `cyan()` for the category picker's running "Selected so far" tally, `green()` for anything the tool found or assumed on the project's behalf (a detected stack signal and its evidence, the auto-detected target tool, the auto-assumed `--root`), `yellow()` for a notice worth a second look without being an error (a stack preset's known coding-standards gap, categories left unreviewed), and `red()` for actual failures (`main()`'s caught-error and usage-error output). Six distinct roles, not one dim/plain split, so the eye can tell what kind of line it's reading without parsing every word.

The same terminal fallback also asks, right after the standards yes/no: **which script standard applies** (TypeScript only / JavaScript only / JS and TS together, pre-selected from a `tsconfig.json` or a `typescript` package.json dependency) and **which of the nine project-wide standards apply** (CSS/HTML/Git/Versioning/SEO/Performance/Accessibility/QA/AI — `askMultiselect`'s new `defaultAll` mode, so pressing Enter keeps all nine instead of picking none; most projects keep every row, this question exists for the real exceptions). Both get written straight into the Active Standards table at protocol-file-creation time via `applyActiveStandards()` — see Step 3 below, which Claude Code chat asks the same two questions for, so neither path leaves the table's placeholders for later manual cleanup.

Every multiselect/detected line also carries a one-line purpose, via `loadSkillPurposes()` reading straight from `skills/README.md`'s own Skill/Purpose tables (truncated to 80 chars; nested markdown links in a cell flatten to their link text, since a relative `.md` path means nothing printed in a terminal), dimmed with an ANSI escape (`dim()`, respects `NO_COLOR`) so it reads as secondary to the skill name next to it rather than blending into one flat line — so a human picking skills in a bare terminal is never choosing bare names blind. Keeping `skills/README.md`'s tables current (the catalogs-to-update-together rule already applies) is what keeps these descriptions accurate; a skill with no matching row just shows its bare name.

## Step 1 — Offer the modes
Ask with `AskUserQuestion` — one single-select question, header "Install mode" — unless the user already said which:
- **Everything** — all skills + the full coding-standards system.
- **Pick** — the universal permanent-pinned group pre-checked (from `skill-scope`), plus the catalog by category (name + one-line purpose from the library README) for the user to choose categories and/or individual skills, plus a yes/no on the standards system.
- **Auto-detect** — universal permanent-pinned group installs unconditionally; for the conditional-pinned group, scan the target project for a project guide doc (`README.md`, `CLAUDE.md`, `AGENTS.md`, `package.json`/`composer.json`/similar manifest, an existing `docs/` folder) against each skill's signal in `skill-scope`'s table (e.g. a Three.js dependency → `stack/threejs-scene`, an Astro config → `stack/astro-page`, a Shopify theme structure → `stack/shopify-toolkit-install`). Present the inferred list with the evidence found (file + line/field) before installing — cite the signal, never pin on a guess. Per-session-archivable skills still install unconditionally in this mode too; only their per-session toggle is deferred to `handover`.
- **Stack preset** — skip the scan; offer the stack names from the table below as the options directly (Astro / Next.js / Laravel, plus "Other" to type one not yet in the table). Installs the universal permanent-pinned group plus the named stack's row, with no detection step — use this when the user already knows the stack (a brand-new project with no files to scan yet, or they just don't want to wait on a scan). State the preset's content before installing, same as Auto-detect states its evidence.

**Pick mode's interaction stays click-first too:** don't dump the full skill catalog as one typed list. First ask an `AskUserQuestion` call with `multiSelect` questions — split the nine categories (`models`, `workflow`, `standards`, `memory`, `stack`, `libraries`, `meta`, `addons`, `mcp`) across as many questions/calls as needed to stay at ≤4 options each, each option carrying its one-line purpose from the library README. For every category the user picks, ask a follow-up `multiSelect` `AskUserQuestion`: if the category holds 4 or fewer skills, list them directly; if it holds more, offer curated bundles instead (e.g. "All of workflow", "Core workflow only (handover, pre-commit, plan-first)", "None") with a final option "Pick individually" that is the only point where the user types specific skill names. Close Pick mode with a single yes/no `AskUserQuestion` for the standards system.

| Stack | Installs | Known gaps (say this plainly, don't fabricate the missing layer) |
|---|---|---|
| **Astro** | `stack/astro-page` skill; full coding-standards system with the `frameworks/astro.md` + `frameworks/astro/` override active (layers 1–3 complete) | None — this stack is fully covered. |
| **Next.js** | Universal group only; coding-standards layers 1–2 (`js-and-ts-standards` or `ts-standards` per the index's Script Standard Selection table, `html-standards` for JSX) | No `stack/` skill and no `frameworks/` override exist for Next.js yet — App Router conventions, Server/Client Component rules, etc. are not encoded anywhere in the kit. Say so, and ask if the user wants that authored as a follow-up; don't invent rules to fill the gap. |
| **Laravel** | Universal group only; `coding-standards/css-standards.md` for any plain CSS, nothing else | The kit has no PHP or Blade standards layer at all — no file-role rules for controllers, models, or Blade views. `html-standards.md` does not cover Blade syntax. Say so plainly in the report; ask if the user wants a PHP/Blade layer authored as a follow-up rather than installing a layer that doesn't exist. |

Add a row here (and to `skill-scope`'s conditional-pinned table, if a real signal exists for it) the next time a stack gets a dedicated skill or framework file — a preset is only ever a named shortcut to real, already-classified content, never a new classification of its own.

Before finalizing any mode, ask via `AskUserQuestion` — yes/no, header "Overrides" — whether the user wants to override anything the scan/pick produced (pin something the scan skipped, or explicitly exclude something it matched). On "yes", collect the specifics as free text (the one point in Step 1 that needs typing, since an override is inherently open-ended) and record it plainly in the install report, since it's the user's explicit statement that authorized it.

**Detect the target tool before any mode proceeds — infer first, then confirm.** Probe the target: `.opencode/` or `opencode.json` → OpenCode; `.claude/` or `CLAUDE.md` → Claude Code; `.agents/` or a bare `AGENTS.md` → Codex/agents.md tools. State the evidence found, then confirm it via `AskUserQuestion` (header "Target tool") with one option per tool the probe actually found evidence for (labeled with that evidence, e.g. "Claude Code — found .claude/ and CLAUDE.md") plus "None of these" to type an answer when nothing was found or markers conflict (an inference never stands unconfirmed — a repo may carry markers for several tools). **Record the answer as this install's target tool — Steps 2, 3, and 4 route every path off it.**

**Path routing — the detected tool decides where files land:**

| Target tool | Skill root | Session-protocol file |
|---|---|---|
| Claude Code | `<target>/.claude/skills/` | `<target>/CLAUDE.md` |
| OpenCode | `<target>/.opencode/skills/` | `<target>/AGENTS.md` |
| Codex / agents.md-convention tools | `<target>/.agents/skills/` | `<target>/AGENTS.md` |

Each tool auto-loads its own instruction file and ignores the other: OpenCode reads `AGENTS.md` and falls back to `CLAUDE.md` only when no `AGENTS.md` exists; Claude Code does the reverse. A session-protocol file in the wrong place is present on disk but permanently unreachable — the install looks complete while every session silently starts blind. Never write the contract into a file the detected tool does not read.

**Multi-tool repos (decided):** keep the full contract in exactly one canonical file — `AGENTS.md` by default, the cross-tool convention — and make the other tool's file a short pointer to it. Never two hand-maintained copies (they drift). Because a pointer depends on the agent following it, the pointer must state in its first line that reading the canonical file is mandatory, and Step 4's reachability check applies to each tool's file. Ask via `AskUserQuestion` (yes/no, header "Second tool") before wiring a second tool; on an OpenCode/Codex-only install, state in the report that Claude Code's `AGENTS.md` fallback is shadowed by any `CLAUDE.md`/`CLAUDE.local.md` (version floor in Step 4) and the pointer is the remedy. Exception: a Claude Code-only project keeps its contract in `CLAUDE.md` as today — no `AGENTS.md` is created unless a second tool is confirmed.

When the user picks, advise but don't push: note skills that travel together (`coding-standards` skill pairs with the standards folder; `memory-gardener` pairs with `memory-bank`; Claude model skills pair with `claude-all-models`; open-model skills pair with `opencode-all-models`; `e2e-scaffold` pairs with `coding-standards/qa/e2e-testing.md` — the skill scaffolds the fixtures/config layer, the standard defines the discipline for keeping it current; `intent-capture` pairs with `plan-first` — it feeds the plan's Goal/Approach line on ambiguous asks; `pre-merge-gate` pairs with `role-session` — it's the self-check run before marking claims `awaiting-review`; `hooks-enforcement` pairs with `coding-standards/ai-standards.md` — it's the Claude Code-only mechanical assist for that file's AI-01–AI-03; `comment-style` pairs with `coding-standards` — its `terse` level matches RULE AI-11 and its exceptions cite TS-15 / JT-TS-05; `agent-usage` pairs with `mode-kernel` — mode-kernel governs how agent-usage's approval gate (and debug-protocol's/coding-standards'/perf-audit's own stop-and-wait gates) behaves per session mode, install together; `agent-usage` also pairs with `handover` — its Reporting contract writes into handover's "Agent handovers" mechanism; `skill-ablation` pairs with `memory-gardener` — gardener prunes what stays, ablation periodically tests what should stay at all; run gardener first if learnings/handover are over cap), and note stack skills that don't fit the target project's stack.

## Step 2 — Install skills (mechanical — run the script, don't hand-copy)
Resolve the final skill-name list first (Step 1's mode, `skill-scope`'s tables, any explicit override), then run:
```
node <library>/skills/meta/install-kit.cli.js install --library <library> --root <target> --tool <detected tool> \
  --skills name1,name2,mcp-manager:stitch,...
```
One call installs every skill in the list **and** its companions, in the flat `<skill-root>/<name>/SKILL.md` layout, verbatim for non-markdown companions, writing the `package.json` CommonJS shield automatically the first time any `.js` companion lands. For a skill where only some companions apply (`mcp-manager`'s per-server files, `system1-prefilter`'s Laya-only script), append `:companion1+companion2` to that skill's name using the companion's *target filename stem* (e.g. `mcp-manager:stitch`, not `mcp-manager:mcp-manager.stitch.md`) — omit the suffix to install every companion. The script never touches `learnings.md` (it only ever exists in a target, never the library) and writes `<target>/.ai-dev-kit.json`, a manifest of exactly what it installed — `update`, `uninstall`, `archive` and `unarchive` all read this to know what's theirs to touch, so every install must go through the script, never a manual copy, or later runs lose track of it.
- If a skill already exists in the target with different content, the script merges in the library's latest file but **carries forward** `comment-style`'s active level automatically (no need to re-pass `--comment-style-level` on a re-install unless changing it) — nothing else needs the old compare-and-ask, since the script never overwrites a file outside what it manages.
- **`comment-style` still asks one question in conversation** (universal, so it always installs; the level is the only choice, decided here — the script just writes it). Ask via `AskUserQuestion` (single-select, header "Comments"), options **none (Recommended)** — the AI writes no comments except rule-mandated ones such as TS `as` justifications and tool directives, **terse** — one short line, only when the why is non-obvious, **descriptive** — up to 3 short plain-language lines for the tricky parts, each carrying that explanation as its description. Pass the answer as `--comment-style-level <level>`. Tell the user it can be changed any time by saying so in-session. If the user already stated a level, don't re-ask.
- **`hooks-enforcement` is Claude Code-only and opt-in beyond the file copy:** if selected, additionally ask via `AskUserQuestion` (yes/no, header "Hook merge") whether to merge its sample hook JSON into `<target>/.claude/settings.json`. On yes, run `node <library>/skills/meta/install-kit.cli.js merge-hooks --library <library> --root <target>` — it reads the three core hook blocks straight out of `hooks-enforcement.md` and merges them in, never overwriting an existing `settings.json` or duplicating an entry already there. Skip this question entirely for non-Claude-Code targets.
- **Tool-compatibility checkpoint (before running the script):** check each selected skill's frontmatter for `compat: <tool>-only`. If the target tool (from Step 1) doesn't match, flag it in the plan before installing and ask via `AskUserQuestion` (header "Incompatible skill") with two options: "Skip it" (it would never trigger there anyway) or "Install anyway" (as inert reference material). A skill with no `compat` field is universal. Report skipped-for-incompatibility items in the Step 4 summary, separate from user-deselected ones.

## Step 3 — Install standards (if selected; still mechanical)
Add `--standards`, `--script-standard <js|ts|js-and-ts>` and `--active-standards <a,b,...|all|none>`, and — if not already set in an existing install — `--context-code <value|none>`, to the **same** Step 2 call (or run it again with just those flags — the script is idempotent):
```
node <library>/skills/meta/install-kit.cli.js install --library <library> --root <target> --tool <detected tool> \
  --skills ... --standards --script-standard ts --active-standards css,html,git,seo,performance,accessibility,qa,ai,design --context-code X7
```
This copies the whole `coding-standards/` folder, and — only if the routed session-protocol file (`CLAUDE.md` for Claude Code, `AGENTS.md` for OpenCode/Codex) doesn't exist yet — creates it from `CLAUDE.example.md` with the template's own preamble and the first `---` already stripped, the Context-code row already filled in or removed, every Skill Triggers row whose skill isn't in the resolved `--skills` list already deleted, the "Parallel-Session Coordination" section already dropped unless `role-session` was in that list, the **Active Standards** table's Script-standard row already resolved to the one file that applies (`--script-standard`), and a row for every standard *not* named in `--active-standards` already removed (`coding-standards/README.md`'s own setup instructions: "remove rows for standards that do not apply" — the script now does that instead of leaving it for later). **It never overwrites an existing session-protocol file**, matching the old never-overwrite rule exactly; if one exists, the script leaves it alone and you fill in the Context code by hand if it's still unset (the trigger/section/standards pruning only runs at creation time, since it reads the skill list and flags from the same `install` call — a later `update` never re-prunes an existing file).
- **Ask for the Context code before running this** (RULE AI-01) via `AskUserQuestion` (single-select, header "Context code"): generate three fresh 2–4 character letter+digit candidates (never reuse a fixed default or a code from another project; avoid common strings like `OK` or `007`) as three options, plus a fourth option "No code (bare [CX])". The tool's built-in "Other" choice is the fallback for a user who wants to type their own instead of picking a candidate — accept only 2–4 alphanumeric characters from it, otherwise re-ask once. Pass the result as `--context-code`.
- **Ask which script standard applies** via `AskUserQuestion` (single-select, header "Script standard"): "TypeScript only" / "JavaScript only" / "JS and TS together", pre-selecting whichever the project scan already points to (a `tsconfig.json`, or `typescript` in `package.json`, suggests TS). Pass the answer as `--script-standard`. Per `index.md`, exactly one applies — never pass more than one.
- **Ask which of the nine project-wide standards apply** via `AskUserQuestion` (`multiSelect`, header "Active standards"): CSS / HTML / Git / Versioning / SEO / Performance / Accessibility / QA / AI, all pre-checked (most projects keep all nine — this question exists for the real exceptions, e.g. a pure API backend with no CSS or HTML). Pass the kept set as `--active-standards a,b,...` (or `all` if nothing was deselected). Framework / CSS Framework rows are **not** covered by this question — they stay as their own placeholder either way; resolve or remove them by hand per the next bullet.
- **What the script still does not do** (finish these yourself, directly in the created file, right after running it): fill in the rest of the project-specific table (name, framework, prefixes, token file paths) by asking or reading the project; resolve or remove the Active Standards table's Framework and CSS Framework rows (the script leaves both untouched regardless of what else was asked).
- **Multi-tool wiring:** only when the user confirms a second tool also works this repo. Keep the contract in one canonical file and make the other tool's file a pointer to it (Step 1, "Multi-tool repos") — write the pointer file yourself, the script doesn't know about multi-tool setups. If `role-session` is installed, its `templates.md` carries a pointer template for each tool's file.
- Note: `handover/PROTOCOL.md` itself (copied from the `role-session` skill's `protocol.md`) and the board/locks scaffolding are created only when the user activates parallel mode, per `role-session/templates.md` — the pointers may briefly reference a file that doesn't exist yet; that's fine.
- **`.gitignore`:** if the target's `.gitignore` names a skill root (e.g. `.claude/skills/`), update it to the routed root so it doesn't keep pointing at a directory that no longer exists after a tool switch. Propose the edit; don't apply silently.
- If the tooling configs were installed (`coding-standards/tooling/`), mention the lint setup exists but do NOT install any npm packages — that's the user's call, made separately.

## Step 3b — Migrate renamed skills (every re-install; mechanical with an approval gate)
The library keeps a rename ledger at `migrations/RENAMES.md` (repo root). On every `update` run, the script compares the target's `.ai-dev-kit.json` manifest against the ledger's **Old name** column itself and reports any match as a *pending* migration — it never renames anything without approval:
```
node <library>/skills/meta/install-kit.cli.js update --library <library> --root <target>
```
If the output lists a pending migration, show the old → new name to the user and ask. On approval, re-run with `--apply-migrations old-name1,old-name2` (or `--apply-migrations all` once the user has approved everything shown). That one flag copies the new-name skill in with its companions, carries `learnings.md` forward from the old folder (the one exception to "never copy learnings" — it's a move within the same project), and deletes the old folder only after the new one lands. Still grep the routed session-protocol file (and any multi-tool pointer file), plus the other skills' text, for the old name and update references by hand — the script only touches skill folders. Report each migration in the Step 4 summary (`old-name → new-name, learnings carried, N references updated`).
When maintaining the library itself: any skill rename/merge MUST add a ledger row in the same change — a rename without a ledger row strands every existing install.

## Step 4 — Verify and report (enforced, not narrated)
The `install` and `update` subcommands both run the verify check internally and return its result — paste the `verify` block from their output verbatim into the report rather than re-running it separately. It mechanically re-checks the flat skill layout, the CommonJS shield for `.js` companions, that the session-protocol file exists and its Context-code placeholder was actually filled in (not just copied), `comment-style`'s active level was actually answered, and `coding-standards/index.md` is present if the folder is. These are exactly the failure modes that "look installed" from the agent's own narration but leave the project silently broken at the next session start.
- **If `verify.ok` is `true`:** report clean, list what was installed where (grouped skills / standards, read straight from the script's own output — don't re-derive it), name the detected target tool and both routed paths explicitly, and move to the suggestions below.
- **If `verify.ok` is `false`:** do not declare the install done. Show every `fail`-level finding, fix what the script's own flags can fix (re-run `install` with the missing `--comment-style-level` or `--context-code`, re-run with a corrected `--skills` list), re-run, and only report success once it is clean. An install that still fails after one fix pass gets reported as "install incomplete: <reason>," never as done with caveats.
- Reachability depends on more than the script can see from one project alone: on an OpenCode/Codex-only install no `CLAUDE.md` is created, so Claude Code would fall back to `AGENTS.md` (needs Claude Code ≥ 2.1.277; ≥ 2.1.281 with telemetry off or on Bedrock/Vertex/Foundry) — but only while no `CLAUDE.md`, `.claude/CLAUDE.md`, `CLAUDE.local.md`, or parent-directory `CLAUDE.md` exists, since any of those shadows the fallback. If the project is later opened in Claude Code, create a `CLAUDE.md` pointer to `AGENTS.md` instead of relying on the fallback. Note this in the report; don't create the pointer on a single-tool install.
- Suggest the natural first actions in the new project: a `handover.md` (if handover installed), the session-protocol project table (if standards installed).
- Tell the user once, in two lines, that skills load by the model's own judgment and sometimes do not (measured: a failing-build prompt loaded `debug-protocol` in about 1 of 6 runs), while the checks that read the actual files do not depend on that: the git hook (`/githooks`, any tool) and, on Claude Code, the `edit-check`, `standards-chain` and `precommit-gate` mods. Offer both; install neither unasked.

## Step 5 — Archive / unarchive (mount / unmount) a skill
`handover` decides, every session, which per-session-archivable skills the stated next task doesn't need — but it should never hand-move those folders. It runs the same script:
```
node <library>/skills/meta/install-kit.cli.js archive   --root <target> --skills name1,name2   # or --all
node <library>/skills/meta/install-kit.cli.js unarchive --root <target> --skills name1,name2   # or --all
```
`archive` moves exactly the named skills (only ones the manifest tracks as currently installed — same protection as `uninstall`) from `<skill-root>/<name>/` to `<tool-dir>/skills-archive/<name>/` (`.claude/skills-archive/` or `.opencode/skills-archive/`, sibling of the skill root, matching `skill-scope`'s existing convention), drops the CommonJS shield once nothing archived still needs it, and records the move in the manifest. `unarchive` reverses it by name (or `--all` to restore everything currently archived), re-adding the shield if a restored skill needs it. A skill the manifest doesn't recognize as installed, or doesn't recognize as archived, is reported back and left untouched rather than guessed at. `handover` records the archived list + paths in `handover.md` as it always did; the script just makes the move itself atomic and reversible instead of a narrated multi-file move.

## Step 6 — Uninstall
```
node <library>/skills/meta/install-kit.cli.js uninstall --root <target> --skills name1,name2   # or --all
```
Removes exactly the skill folders the manifest (`.ai-dev-kit.json`) recorded this kit as having installed — never a folder the manifest doesn't know about, even if `--all` is passed, so a hand-authored or third-party skill living in the same skill root is always left alone. Drops the `package.json` CommonJS shield once no remaining companion needs it. **Never removes `coding-standards/` or the session-protocol file by default** — pass `--remove-standards` to also remove `coding-standards/`; the session-protocol file is never deleted by the script under any flag, since it may carry project-specific edits beyond what the kit wrote. If the user wants it gone too, remove it yourself after confirming with them, not automatically. Report what was removed and what was deliberately left, straight from the script's `removed`/`kept` output.

## Keeping installs current
This copies a snapshot, tracked by the manifest. When the library improves, or the user wants more skills, commands, addons or mods later, run `update` (add `--skills` for specific ones, or `--all` to resync everything the manifest already tracks) — the manifest ensures only kit-managed files move. Never edit an installed copy directly for library-wide improvements; edit the library and re-install/update.
